Quick start

The shortest path from installed to brewing.

1. Add the integration. Settings → Devices & Services → BKON Brewer. It discovers the machine over Bluetooth, or tick Simulate to explore with no hardware.
2. Open a recipe. Four grounded defaults are ready (Classic Pour Over, two teas, medium-roast coffee). Read one with get_recipe.
3. Brew it. bkon_brewer.brew_saved with the recipe name — from a dashboard button, an automation, or Assist.
4. Tune it. Ask the concierge "make it stronger" and save the result.
5. (Optional) Smarter answers. Install the LightRAG add-on for semantic Q&A — see Semantic Q&A.
No brewer yet? The integration runs in Simulate mode — every entity, button, and service works against a scripted brewer, so you can learn the whole interface before the hardware arrives.

The concierge

Talk to it by voice through Assist, or with the ask service. It figures out what you want and routes accordingly.

tune "make my Morning Cup stronger"

Deepens the vacuum and lengthens the steep — grounded in the RAIN guide's own relationships, bounded to the documented ranges — previews the change, and never overwrites without you saving.

answer "how do I descale the machine?"

Answered from the brewer's service documents, with the source named. Built-in keyword retrieval by default; semantic when the add-on is installed.

diagnose "it says not sealed" · "what's C:3 M:5?"

Cause and next step: "Chamber not sealed — reseat the chamber; a vacuum can't form if it isn't."

The trick it gets right: "make my cup stronger" tunes a recipe, but "how do I make coffee stronger?" answers a question — both contain "stronger". When it's genuinely ambiguous, it asks rather than guessing.

Something wrong with the machine

Diagnose

Give it an error code, a status, or just describe what the brewer is doing. It reads the confirmed fault table first, then the machine's own service documents, and tells you the likely cause and what to try.

Recipes & git

Recipes are durable, named objects in the app's own schema — and files you can put in version control.

The step types

Start — heat to a temperature (°F)
Fill — fill & rinse volumes (ml), atmospheric pause (ap)
Vacuum — strength (kPa) & hold time — the machine's signature
Purge — pressure, hold, detection
Dialog — pause and prompt the operator

The git round-trip

bkon_brewer.export_recipes   # one JSON per recipe, deterministic
git add recipes/ && git commit   # a recipe edit is a one-file diff
bkon_brewer.import_recipes   # load them back, each validated

Export is byte-stable, so re-exporting an unchanged library leaves git clean, and editing one recipe is a one-file change a reviewer can read.

Longer recipes

A Bluetooth brew is capped at 599 bytes. Loading a recipe as a file is not.

PathTransportSize limit
Brew nowBluetooth599 bytes
Menu fileUSB — Service Menu → Update Recipe Filenone observed

bkon_brewer.export_menu writes all recipes as one menu object in the machine's own vocabulary — every recipe, every portion, with no 599-byte ceiling.

It is not yet a loadable file, and the docs used to imply it was. The service documentation describes the real path: menus are authored in BKON's Craft Cloud and a Compile step produces a .bbp file — name no more than eight characters — which is what goes on the thumb drive. The machine ingests that compiled container, not arbitrary JSON, and this project cannot produce one: the format is unknown. Treat the export as the recipe data in the machine's own terms. Capturing a real Export to Recipe File from a unit would settle both the container and the folder layout at once.

Exporting a menu file

Experimental — treat the output as a draft, not a menu. bkon_brewer.export_bbp writes the library as a .bbp at /local/bkon/hamenu.bbp. The checksum and every step record are confirmed against real device files and round-trip exactly; the category framing is inferred and has never been accepted by a brewer. The USB path writes to flash on the user-interface board — so don't load this onto hardware you can't recover. Its honest use is as something to diff against a genuine Service Menu → Export to Recipe File dump, which is exactly what would confirm the framing and make this safe.

The call reports a self-check saying which parts it can vouch for:

service: bkon_brewer.export_bbp
data:
  menu_name: Home Assistant
  filename: hamenu.bbp      # 8 characters or fewer, plus .bbp

Architecture

Local-first. The cloud is optional and only touches question-answering.

You ─ voice / dashboard / service call
              │
    ┌─────────┴──────────┐
    │  HA integration    │   entities · services · concierge
    └────┬───────────┬───┘
         │ Bluetooth  │ HTTP (optional)
         ▼            ▼
    The brewer    LightRAG add-on ── Ollama / Anthropic / OpenAI
  (Nordic UART    (local embeddings,   (generation)
   via a proxy)    graph retrieval)

The logic that matters — encoding, the advisor, retrieval, provider selection, the recipe schema — is pure and tested (404 assertions, no dependencies). I/O layers are thin and clearly marked where they're unverified against hardware.

The HA host has no Bluetooth radio, so the brewer is reached through an ESPHome Bluetooth proxy — transparent to the integration.

Protocol

Nordic UART, with an XML-tag payload the machine parses.

RoleUUID
Write (host → brewer)6e400002-…
Notify (brewer → host)6e400003-…

A recipe on the wire

{msg:1:<START><TMP>205</TMP></START><FR><FWV>250</FWV>…</FR>…<BO><BT>4</BT></BO>}

Each step's type and value keys are uppercased into tags and concatenated — the same form as a manual command, not JSON. Events come back as stepCompleted, recipeCompleted, dialog:…, is_connected:0/1.

Still needs a real brewer

Some of this is inferred from the app binary and awaits a hardware capture: the recipe wire form (well-evidenced), the dialog-response frame (the msg:3 lead), and BLE chunking. The send_raw service is the test hook.

Confirmed from the service documentation

Units & error codes

The facts an integration actually needs, established from an archive of 53 service and training documents for this machine. What follows is what those documents settled — units, ranges, fault meanings — not their contents.

Units

These retired the largest open question in the protocol: every value is a bare number on the wire, so the unit had to come from somewhere.

FieldUnitTypical operating values
Temperature tmp°F, to ±1 °F~165–205 °F (documented tea menus)
Fill / rinse fwv rwvmillilitres~35–250 ml
Vacuum ps (on vc)kilopascals~20–24 kPa in base recipes
Steep / pause / hold tm ap dlsecondsa few seconds to ~15 s
Purge pressure is the exception. The ps value on a purge step is not confirmed to be kPa. The vendor app accepts only 25–35 for it (real menus use ≈30), so the builder holds it to that band even though the unit is unknown.

What the app actually accepts

The units above are what the guide documents. The vendor app's step editors go further — they validate every field before syncing, so a value the app rejects is one the machine is unlikely to take. Reading those validators corrected several bounds this project had guessed, and turned up two fields it was missing:

FieldApp acceptsWe had
Temperature140–212 °F (also 60–100 °C)165–210
Vacuum ps0–60 kPa0–101
Purge ps25–350–100, default 50
Fill / rinse0–600 ml0–999
All times0–180 s180 ✓
Vacuum pause appresent — 0–180 smissing

The recipe studio's builder now uses these ranges, and its vacuum and purge steps carry the pause and rinse fields. The Celsius switch is display-only: the app converts with F = C·9/5 + 32 before sending, so the wire is always Fahrenheit.

How vacuums relate in a sequence

Reference material for designing a recipe, not something the protocol enforces — but it tells you the sensible neighbourhood for a value, which a bare min/max cannot. If the first vacuum is X kPa, the next sits around X+2 and the one after around X+1, with steep times tuned per menu.

The base tea recipes are published as starting points: the low-temperature menu begins at 175 °F / 24 kPa, the high-temperature menu at 205 °F / 20 kPa — so a hotter brew starts from a shallower vacuum, not a deeper one. Delicate leaf teas (broken-leaf Sencha, Gyokuro, first-flush Darjeeling) get a different shape entirely: one vacuum, a much shorter steep, and most of the water front-loaded, because the repeated vacuums of a standard recipe would over-extract them.

The dial-in convention

Recipes are named temp/vacuum/steep — 185/0/0 is the category mid-point, 185/+2/0 a little more concentration, 185/-2/+10 lighter but more intense. The rule of thumb behind it:

Vacuum moves in big steps of ±2 kPa — it changes concentration.
Steep moves in small steps of ±5 or ±10 s, at the end of the recipe — it changes flavour intensity.
This confirmed the concierge's arithmetic after the fact. The advisor was written to move the vacuum by 2 kPa and the steep by 5 s per request — those were reasoned guesses, and they turn out to match the documented convention exactly. It is why "stronger" reaches for the vacuum and "less bitter" reaches for temperature and steep time.

The vacuum is the machine's distinguishing mechanism — extraction under reduced pressure, held for only seconds — which is why it is a first-class step here rather than a variant of purge, and why "stronger" moves it first.

Error codes

Reported as C:code M:module — C is the fault, M is the module that raised it, so the module repeats down a group. Ask the concierge "what does C:3 M:5 mean?" and you get the row below plus a fix; these are also what sensor.*_last_error renders.

Provenance

The vendor is Franke — the service documents carry their copyright, and BKON's brewer line is theirs. The archive is the owner's private mirror of documents for a machine they own; it is referenced, never vendored. Nothing here depends on it at runtime, and every fact above would be equally true read off the machine's own display. No vendor document text or application source is in this repository.

The service documents describe installing, operating and repairing the machine — not talking to it over Bluetooth. So they left the open protocol questions (chunking, {msg:N} numbering, the dialog-response frame) exactly where they were: needing a live capture. See Fidelity & status.
Recovered from real device files

The .bbp menu file

The machine's on-board menu is a .bbp file loaded over USB — the route to recipes larger than Bluetooth allows. Three real ones turned up inside a vendor software-update package, and most of the format now reads cleanly.

Understood, but not yet safe to write. The step records, the tag vocabulary and the checksum are confirmed byte-for-byte. A few header and category field widths are not. The installer flashes this file to the user-interface board, and a malformed one is written to the same place a good one is — so this is documentation, not a feature. See what that means for export_menu.

The container

0       4   magic: "BKON" (beverage menu) or "BKOn" (service menu)
4       4   u32le, always 12 — header length or version
8       …   body
end-4   4   u32le checksum over every preceding byte

The checksum — solved

The trailing four bytes are JAMCRC: an ordinary CRC-32 with the final complement left off — equivalently, its bitwise inverse — little-endian, over the whole file except the trailer. Nothing standard matched until this did, on all three files at once.

trailer = struct.pack("<I", zlib.crc32(body) ^ 0xFFFFFFFF)
FileTrailer~crc32(body)
Ser82018.BBP0x995edc9b0x995edc9b
FrkMenu.BBP0x1a6bbd460x1a6bbd46
MENU.FBP0xe907b6a70xe907b6a7

Steps — the part that matters

A step is u32le type, u8 tag length, then the tag. 3 461 of them parse cleanly across the three files, and every one re-encodes to the exact bytes it came from.

TypeStepTags
0Start / heat<TMP>
1Fill<FWV> <RWV> <AP>
2Vacuum<PS> <TM> <AP>
3Purge<PS> <TM> <DET> <CONTR>
4Brew out<BT>

A real portion, straight out of the file:

[0] <TMP>170</TMP>
[1] <FWV>300</FWV>
[2] <PS>28</PS><TM>7</TM>
[1] <FWV>25</FWV><RWV>25</RWV><AP>20</AP>
[3] <PS>30</PS><TM>20</TM><DET>1</DET><CONTR>1</CONTR>
[1] <RWV>70</RWV>
[4] <BT>4</BT>
This graded our own homework. Three decisions in the recipe encoder were inferred from the vendor app and are now confirmed against real device files: the wire form is uppercase tags, not JSON; the fill pause is AP, not DL — a bug this project had and fixed earlier from app data; and the purge flags really are DET and CONTR spelled out.

Structure

Strings are length-prefixed — two bytes for category names, one for recipe names, codes and portion names.

category := name, 4-byte colour, recipe count, recipes…
recipe   := name, code, portion count, portions…
portion  := name (small/medium/large), step count, steps…

Recipe names can contain a newline, which the machine renders as a two-line button ("Sencha \nDLT"). The code field carries the dial-in name from the menu development guide — "170/0/10 FGT". Unused buttons are real records named Empty with zero portions, so a menu is a fixed grid, not a sparse list — which is what the 8 × 4 × 8 capacity means in practice.

Two kinds of file, and how one is installed

BKON is a beverage menu; it opens with machine parameters as plain tags (<ASF>, <TBH>, <KPVAL> — control constants) before the categories. BKOn, with a lowercase n, is a service menu whose "recipes" are diagnostic routines: Neg Pressure Leak Test, Tower, WVSC.

The update package's INSTALL.INI names the target outright, which settles the USB layout question the docs previously left open:

[Menu]
name=Menu Resource
file=0:TeaBrew/MENU.FBP
type=flash
device=Flash0
address=0x80000000

So the stick needs a TeaBrew/ folder with its own INSTALL.INI and a second one at the root pointing to it — the layout is load-bearing. The interface is a third-party product (TeaBrewer, by M-Wave Controls), which is why this format looks nothing like the Bluetooth protocol. And the eight-character filename rule holds: FrkMenu, Ser82018, MENU.

Still open

Header bytes 8–15 and the category-table field widths — a guess parses the first category then drifts.
Whether the machine checks anything beyond the checksum.
A <DESCALE>/<DV> start variant (seen in a descale routine).
One unmatched brew-out: the service menu balances 111/111, both beverage menus come out 123/124. Unexplained, so it is written down rather than rounded off.

The clean way to close all of it is the machine's own Service Menu → Export to Recipe File: a known-good file from your unit would confirm the framing and give a byte-for-byte target to reproduce.

Fidelity & status

How faithful this is to the app, and what's proven versus inferred.

Matches the app

Framing, the recipe serialization rules, the recipe schema, the 599-byte basis, and the step-progress model all match the vendor app, checked against its recovered source.

Fixed by auditing

The brew path was sending JSON; the app converts recipes to XML step-tags. Corrected — the manual-command path was always right.

Honest unknowns

The dialog-response frame and BLE chunking need a hardware capture. None of it has touched a real brewer yet; the pure logic is tested, the I/O is marked where it's inferred.
