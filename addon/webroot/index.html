Quick start

The shortest path from installed to brewing.

1. Add the integration. Settings → Devices & Services → BKON Brewer. It discovers the machine over Bluetooth, or tick Simulate to explore with no hardware.
2. Open a recipe. Four grounded defaults are ready (Classic Pour Over, two teas, medium-roast coffee). Read one with get_recipe.
3. Brew it. bkon_brewer.brew_saved with the recipe name — from a dashboard button, an automation, or Assist.
4. Tune it. Ask the concierge "make it stronger" and save the result.
5. (Optional) Smarter answers. Install the LightRAG add-on for semantic Q&A — see Semantic Q&A.
No brewer yet? The integration runs in Simulate mode — every entity, button, and service works against a scripted brewer, so you can learn the whole interface before the hardware arrives.

The concierge

Talk to it by voice through Assist, or with the ask service. It figures out what you want and routes accordingly.

tune "make my Morning Cup stronger"

Deepens the vacuum and lengthens the steep — grounded in the RAIN guide's own relationships, bounded to the documented ranges — previews the change, and never overwrites without you saving.

answer "how do I descale the machine?"

Answered from the brewer's service documents, with the source named. Built-in keyword retrieval by default; semantic when the add-on is installed.

diagnose "it says not sealed" · "what's C:3 M:5?"

Cause and next step: "Chamber not sealed — reseat the chamber; a vacuum can't form if it isn't."

The trick it gets right: "make my cup stronger" tunes a recipe, but "how do I make coffee stronger?" answers a question — both contain "stronger". When it's genuinely ambiguous, it asks rather than guessing.

Recipes & git

Recipes are durable, named objects in the app's own schema — and files you can put in version control.

The step types

Start — heat to a temperature (°F)
Fill — fill & rinse volumes (ml), atmospheric pause (ap)
Vacuum — strength (kPa) & hold time — the machine's signature
Purge — pressure, hold, detection
Dialog — pause and prompt the operator

The git round-trip

bkon_brewer.export_recipes   # one JSON per recipe, deterministic
git add recipes/ && git commit   # a recipe edit is a one-file diff
bkon_brewer.import_recipes   # load them back, each validated

Export is byte-stable, so re-exporting an unchanged library leaves git clean, and editing one recipe is a one-file change a reviewer can read.

Longer recipes

A Bluetooth brew is capped at 599 bytes. Loading a recipe as a file is not.

PathTransportSize limit
Brew nowBluetooth599 bytes
Menu fileUSB — Service Menu → Update Recipe Filenone observed

bkon_brewer.export_menu writes all recipes as one menu file in the machine's own format. Copy it to a thumb drive, load it through the Service Menu, and a recipe with many steps that would never fit a Bluetooth brew lives in the on-board menu instead.

The exact on-USB folder layout isn't fully confirmed. The service uses the machine's own recipe-object shape; capture a real "Export to Recipe File" from the unit to verify the surrounding layout before relying on it.

Architecture

Local-first. The cloud is optional and only touches question-answering.

You ─ voice / dashboard / service call
              │
    ┌─────────┴──────────┐
    │  HA integration    │   entities · services · concierge
    └────┬───────────┬───┘
         │ Bluetooth  │ HTTP (optional)
         ▼            ▼
    The brewer    LightRAG add-on ── Ollama / Anthropic / OpenAI
  (Nordic UART    (local embeddings,   (generation)
   via a proxy)    graph retrieval)

The logic that matters — encoding, the advisor, retrieval, provider selection, the recipe schema — is pure and tested (252 assertions, no dependencies). I/O layers are thin and clearly marked where they're unverified against hardware.

The HA host has no Bluetooth radio, so the brewer is reached through an ESPHome Bluetooth proxy — transparent to the integration.

Protocol

Nordic UART, with an XML-tag payload the machine parses.

RoleUUID
Write (host → brewer)6e400002-…
Notify (brewer → host)6e400003-…

A recipe on the wire

{msg:1:<START><TMP>205</TMP></START><FR><FWV>250</FWV>…</FR>…<BO><BT>4</BT></BO>}

Each step's type and value keys are uppercased into tags and concatenated — the same form as a manual command, not JSON. Events come back as stepCompleted, recipeCompleted, dialog:…, is_connected:0/1.

Still needs a real brewer

Some of this is inferred from the app binary and awaits a hardware capture: the recipe wire form (well-evidenced), the dialog-response frame (the msg:3 lead), and BLE chunking. The send_raw service is the test hook.

Semantic Q&A

Optional upgrade: a graph-RAG service that reads the documents semantically and writes answers with a model you choose. Local embeddings; the cloud is used only for generation.

PartWhereWhy
EmbeddingsLocal (bundled, CPU)Cheap, private, no server
GenerationOllama / Anthropic / OpenAI-compatibleA Pi can't run a big model; pick a provider
OrchestrationLocal (LightRAG)Graph retrieval + generation

The upgrade can never be a downgrade: every question falls back to the built-in retriever if the service is slow or down. Provider selection is a config change — no vendor SDK is baked in — following the same pattern as the sibling apps.

Set it up via the add-on (this page's own home is served through that add-on's Home Assistant ingress). Full steps in the add-on docs and docs/RAG.md.

Fidelity & status

How faithful this is to the app, and what's proven versus inferred.

Matches the app

Framing, the recipe serialization rules, the recipe schema, the 599-byte basis, and the step-progress model all match the vendor app, checked against its recovered source.

Fixed by auditing

The brew path was sending JSON; the app converts recipes to XML step-tags. Corrected — the manual-command path was always right.

Honest unknowns

The dialog-response frame and BLE chunking need a hardware capture. None of it has touched a real brewer yet; the pure logic is tested, the I/O is marked where it's inferred.

Provenance

No vendor application source or document text is in the repository. The document index is built locally and git-ignored; facts (units, error codes) are folded in from the owner's own archive.
